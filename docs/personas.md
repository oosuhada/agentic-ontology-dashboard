# Factory Signal Board Personas

## 1. 문서 목적

이 문서는 현재 구현된 첫 vertical slice인 `매니저 / 엔지니어`의 판단 흐름을 고정한다. 두 역할이 전체 제품 역할을 의미하지는 않는다. 고객사 임원, 현장 작업자·정비 기술자, 데이터 사이언티스트, 품질·감사 담당, 비전문가 고객과 조직 관리자를 포함한 확장 조사와 근거는 [`role-needs-research.md`](./role-needs-research.md)에 정리한다.

사용자별 차이는 단순한 권한 차이가 아니라, 같은 설비 사건을 해석하는 정보의 순서·깊이·행동의 차이이다.

# 2. Primary Persona A — 설비·생산 매니저

## 2.1 프로필

- 가칭: 김현우 매니저
- 역할: 생산 라인 또는 설비 운영 책임자
- 책임: 생산 차질 최소화, 위험 설비 우선순위 결정, 점검·정지 판단, 담당자 지시
- 분석 전문성: 모델과 통계의 세부 원리보다는 운영 판단에 익숙함
- 사용 빈도: 교대 시작, 일일 회의 전후, 이상 알림 발생 시

## 2.2 핵심 질문

- 지금 가장 먼저 확인해야 할 설비는 무엇인가?
- 현재 상태가 실제 조치를 요구하는가?
- 생산에 어떤 영향이 예상되는가?
- 누구에게 무엇을 요청해야 하는가?
- 이 판단의 근거를 짧게 설명할 수 있는가?

## 2.3 성공 기준

- 30초 안에 위험 설비의 우선순위를 이해한다.
- 모델 점수를 해석하지 않고도 권장 결정을 이해한다.
- 판단 근거와 불확실성을 함께 확인한다.
- 엔지니어에게 전달할 조치 요청을 남길 수 있다.
- 필요할 때만 기술 상세로 내려간다.

## 2.4 불편과 위험

- 센서 차트가 너무 많으면 핵심 결정을 놓친다.
- 정확도·F1·SHAP 같은 용어만 제공되면 업무 의미를 이해하기 어렵다.
- LLM이 단정적으로 말하면 과도한 정지 또는 불필요한 점검으로 이어질 수 있다.
- 위험 점수만 있고 생산 영향이나 우선순위가 없으면 행동을 결정하기 어렵다.

## 2.5 기본 화면 정보 순서

1. `PriorityList`
2. `StatusSummary`
3. `RiskKpi`
4. `ImpactSummary`
5. `ManagerDecisionCard`
6. `RecommendedActions`
7. 필요 시 접힌 근거·차트·`ModelDetails`

## 2.6 대표 행동

- 계속 운전하며 모니터링
- 점검 요청
- 계획 정지 검토
- 즉시 정지 검토를 담당 조직에 요청
- 담당 엔지니어 지정
- 판단 메모 남기기
- 상세 근거 열기

## 2.7 반드시 피해야 할 UX

- 첫 화면에 혼동행렬과 모델 실험 결과 노출
- 위험 확률만 제시하고 행동 기준을 제공하지 않음
- 센서 원시값을 설명 없이 나열
- 불확실한 원인을 확정 사실처럼 표현
- 사용자의 승인 없이 실제 설비 제어 또는 작업 지시 실행

# 3. Primary Persona B — 설비·공정 엔지니어

## 3.1 프로필

- 가칭: 박지민 엔지니어
- 역할: 설비 상태 분석과 현장 점검 담당
- 책임: 이상 원인 후보 확인, 점검 수행, 조치 결과 기록, 매니저 보고
- 분석 전문성: 센서 단위·설비 메커니즘·추세 해석에 익숙함
- 사용 빈도: 배정된 이상 사건 확인, 현장 점검 전후, 보고 작성 시

## 3.2 핵심 질문

- 어떤 센서가 언제부터 정상 범위를 벗어났는가?
- 위험도를 올린 주요 변수는 무엇인가?
- 변화가 일시적 노이즈인가 지속적인 이상인가?
- 예상 고장 유형과 점검 순서는 무엇인가?
- 매니저에게 어떤 근거로 보고해야 하는가?

## 3.3 성공 기준

- 이상 발생 구간과 주요 센서를 빠르게 찾는다.
- 현재 값과 정상 범위, 위험 기여 방향을 함께 확인한다.
- 모델 설명과 유지보수 지식이 구분되어 표시된다.
- 점검 체크리스트와 진행 상태를 기록한다.
- Evidence Package에 근거한 매니저용 요약을 생성한다.

## 3.4 불편과 위험

- 자연어 요약만 있고 원시 근거가 없으면 신뢰하기 어렵다.
- 차트에 이상 구간이 표시되지 않으면 분석 시간이 늘어난다.
- 모델 근거와 매뉴얼 권고가 섞이면 인과관계를 오해할 수 있다.
- 데이터 품질 문제를 실제 이상으로 오인하면 불필요한 점검이 발생한다.

## 3.5 기본 화면 정보 순서

1. `StatusSummary`
2. `SensorLineChart`
3. `AnomalyTimeline`
4. `FactorContribution`
5. `EvidenceTable`
6. `EngineerChecklist`
7. `RecommendedActions`
8. `ModelDetails`

## 3.6 대표 행동

- 이상 구간 확대
- 센서 간 비교
- 점검 체크리스트 시작·완료
- 현장 메모 기록
- 원인 후보 상태 변경
- 매니저 보고용 요약 생성
- 데이터 품질 이슈 등록

## 3.7 반드시 피해야 할 UX

- 주요 근거 없이 고장 유형만 출력
- 정상 범위와 단위를 누락
- LLM 문장을 모델의 직접 출력처럼 표현
- 데이터 품질 경고를 숨김
- 근거 없는 점검 항목을 자동 생성

# 4. Secondary Persona — 모델·데이터 검증 담당

## 4.1 역할

모델 개발자 또는 데이터 분석가는 최종 제품의 주 사용자는 아니지만, 모델 버전·임계값·Gold 시나리오 실패를 검증할 수 있어야 한다.

## 4.2 필요한 정보

- 모델 버전과 학습 데이터 버전
- Precision, Recall, F1, Average Precision
- 선택된 운영 임계값과 선택 근거
- 피처 목록과 데이터 누수 검사 결과
- Gold 시나리오별 기대값과 실제값
- 리포트 수치 추적성 검사 결과

## 4.3 제품 표면

이 정보는 매니저·엔지니어의 기본 화면이 아니라 다음 중 하나로 분리한다.

- 접힌 `ModelDetails`
- 별도 관리자 검증 화면
- 평가 결과 파일과 CI 리포트

# 6. 동일 사건의 역할별 표현 예시

## 사건

- 설비: M-014 절삭 설비
- 상태: 공구 마모 위험
- 주요 근거: 공구 마모 값 증가, 토크와 공구 마모의 상호작용 상승
- 신뢰 수준: 중간 이상

## 매니저 표현

> M-014의 공구 마모 위험이 운영 기준을 넘어섰습니다. 현재 생산 영향은 중간 수준이며, 다음 교대 전 현장 점검을 요청하는 것이 권장됩니다. 즉시 정지가 필요한 수준으로 단정할 근거는 없습니다.

필수 블록:

- `StatusSummary`
- `RiskKpi`
- `ImpactSummary`
- `ManagerDecisionCard`
- `RecommendedActions`

## 엔지니어 표현

> 최근 구간에서 공구 마모 값이 기준 범위를 넘어 증가했고, 토크×공구 마모 지표가 위험도 상승의 가장 큰 근거로 계산되었습니다. 공구 상태, 토크 센서와 가공 부하를 순서대로 점검하십시오.

필수 블록:

- `SensorLineChart`
- `AnomalyTimeline`
- `FactorContribution`
- `EvidenceTable`
- `EngineerChecklist`

# 7. Persona 기반 완료 조건

- 동일한 Gold 사건에서 역할별 첫 화면 블록 순서가 다르다.
- 매니저는 기술 상세를 보지 않고도 권장 결정을 이해할 수 있다.
- 엔지니어는 자연어 설명의 모든 핵심 문장을 센서·근거 값으로 추적할 수 있다.
- 저신뢰·데이터 오류 사건에서 두 역할 모두 단정 대신 보류·추가 확인을 안내받는다.
- 사용자의 역할이 달라도 상태·확률·근거의 원본 값은 서로 모순되지 않는다.
